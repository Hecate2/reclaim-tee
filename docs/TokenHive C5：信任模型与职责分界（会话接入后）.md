# TokenHive C5：信任模型与职责分界（会话接入后）

## 0. 术语约定（首次出现时给出全称，后文直接使用缩写）

TEE 即可信执行环境；TLS（Transport Layer Security）为传输层安全协议；OAuth 为开放授权标准；WebSocket 为一种在单条 TCP 连接上提供全双工通信的应用层协议；SSE（Server-Sent Events）为服务器推送事件流；CBOR（Concise Binary Object Representation）为确定性二进制编码（RFC 8949）；Policy 为「凭证使用授权」的签名描述；RateCard（费率卡）为记录定价数据的费率卡；JobSpec 为 Hub 交给 TEE 的作业描述；Receipt 为 TEE 签发的带证据的作业回执；ProviderSeq 为 TEE 内的单调序号；attestation（远程证明）为 TEE 向外部证明自身代码与配置身份的证据机制。

---

## 1. 授权主体：部署运营方

TokenHive 全链路里唯一有资格决定「TEE 可以用谁的凭证访问哪些接口」的主体是部署运营方——既不是 Hub，也不是单个用户（tenant）。

授权发生在部署期而非请求期。运营方预先定义一套 Policy，每份 Policy 把某个 Provider 的 OAuth 凭证绑定到一条准入规则：仅允许访问该 Provider 的 chat/completions、messages、responses 等对话类接口；对会话类请求，仅允许向 /v1/realtime 发起一次 HTTP Upgrade 握手。Policy 随 TEE 部署配置加载进 TEE，其哈希被绑定进 attestation measurement——即 TEE 向外证明自身身份时，这份准入白名单本身就是被证明内容的一部分。Provider 在交付凭证时只信任规定的 TEE 镜像及其 measurement 所承载的这份 Policy，除此之外别无信任根。

这个安排有两个直接后果。其一，Hub 在授权链里只是「凭证的保管与投递方」，不是「授权的决定方」——Hub 无法新增一条不存在的准入路径，也无法让 TEE 越界访问 Provider 的其它接口。其二，请求期的用户（tenant）即便持有合法密钥，也决定不了 TEE 能用谁的凭证做什么；用户能调用的模型与接口，由运营方装载的 Provider 资产与 Policy 共同决定。把「谁授权」「何时授权」都钉死在部署期，是为了让 Provider 对一个静态、可证明、可审计的准入面背书，而不是对运行时某个可疑的调用背书。

## 2. TEE 的最小职责

TEE 的核心职责收敛为一条：**只负责与源头 AI 服务商建立并保持连接，其余一切都不是它的职责。**

JobSpec 是纯粹的「要执行的 HTTP 请求」描述，不携带任何计费或租户字段——没有 model、没有 tenant、没有账务引用；当前键号连续编号 1–14。随之而来的健壮性收益是：TEE 不需要理解 model 与 tenant，也就不存在 TEE 侧对它们的误用或泄露。

整体形态一句话概括：**TEE 不可见 model，不可见 tenant，不可见账务，不解析任何会话内容；它可见的只有凭证、TLS 密钥、Policy、以及请求与响应的明文字节。** TEE 要证明自己值得信任，只需证明「我在凭这份 Policy、当着这份 measurement，把我被授权的连接建立起来并如实搬运字节」。

## 3. 会话接入 Hub 后的信任边界

流式会话在 C5 之前是 TEE 与原计划之间的空白地带；C5 把它的边界画定如下。用户对 Hub 的 /v1/session 端点建立一条 WebSocket；Hub 从会话的第一帧读出 model，据此按最低价选定 Provider，再经 TEE 的流通道与上游的 /v1/realtime 建立全双工会话。此后 Hub 在两条独立的方向上搬运字节——上行把用户帧重新封装成合法的掩码客户端帧交给 TEE，下行把 TEE 透传回来的上游服务端帧解码后以新消息回给用户。

这条边界的要害是「frame 语义的归属」。TEE 的流通道是一条不透明管道：它只认字节，不认帧。所以凡是需要理解 WebSocket 帧的地方——上行用什么 opcode、长度怎么编码、掩码键如何施加、下行读到 close 帧即止——都由 Hub 负责。好处是迁移性与隔离性同时拿到：换一个上游格式只改 Hub 的帧适配层，TEE 不动；而 TEE 即便被攻破，能泄露的也只是一段被计量、被摘要的密文管道，不触及任何一方的明文协议细节。

会话的收尾同样遵循「计价归 Hub」。上游关闭后 TEE 签发会话回执，StatusCode 记 101，RequestBytes 与 ResponseBytes 分别记上行与下行字节总量，StreamHash 摘要下行明文。Hub 拿到回执后先验签、比对实际转发的字节与哈希、再计算有效的会话价并结算入账。回执对不上实际转发字节的一律不结算——这是「Hub 不会为没有真实发生的会话买单」的兜底。

## 4. Hub 侧会话边界：资源不乱进账本

TEE 对会话透明中继、不做任何资源限制，于是「无限消耗站得住脚」的护栏由 Hub 自设。C5 在 Hub 侧实现了三类会话边界，全部在 Relay 引擎里生效：会话全程的墙钟超时、下行字节上限、下行静默看门狗。任一界被触发，会话即被切断。

字节上限有一个刻意选择的计价语义：截断即不结算。原因在于上限以下、上行与下行的摘要不可调和——TEE 已经把越过上限的字节纳入了自己的摘要，而它从未被中继给用户，Hub 无法拿一份与自身中继字节对得上的回执来入账。这种情况下 Hub 切段会话、不收费、不落回执，宁可放走一次会话也不接受「账目与事实不符」（对应「断流 0 计价」）。墙钟超时与静默看门狗则走完全不同的路径：它们切断的是「没等到任何会话结束信号」的悬置状态，若 TEE 仍凭据可查回执则照常结算，否则不结算。三者落点是同一个原则——结算是回执与事实双重印证的结果，不是流程走到哪就算哪。

## 5. Provider 侧审计路径

Provider 需要在事后独立确认「我的凭证没有被越权使用」。C5 之后这条路径由四段相互独立的证据拼接而成，每一段都可由 Provider 自行核对。

第一段，出口一致性。到上游的连接永远经 Provider 自己的 Agent 走出去，上游看到的源 IP 是 Provider 出口地址。Provider 可据此核对：凡是声称「经我授权」的流量，其来路确实是我的出口，而非某个可冒用的中间节点。

第二段，Policy 白名单的执行。Policy 哈希绑进 attestation measurement，因此当 Provider 校验 TEE 的远程证明时，它同时证明了「TEE 装载的准入规则正是我签署的那一份」。TEE 在请求到达上游之前就执行白名单判定——不在白名单内的路径根本不会被写出——所以 Provider 看到的请求集合，必然落在它签署过的那份 Policy 之内。

第三段，回执签名与字节摘要。每次请求与每笔会话都得到 TEE 以自身密钥签名的回执，其中绑定请求正文哈希与响应字节的流式摘要。Provider 可以把 TEE 上报给上游的请求、上游实际返回的响应，与回执里签死的摘要逐一比对，从而确认「TEE 向我们如实报告了它实际收发的东西」，而不是事后造假补一张账。

第四段，凭证用途自证。既然 JobSpec 里已不再携带任何计费元数据，Provider 审计时看到的是一份纯粹的网络操作描述——「用凭证 A 访问路径 B 的 C 接口」。这份描述不含 model、不含 tenant，因此 Provider 不需要相信任何账务中间层，只需核对「凭证只被用于约定的接口」。四段证据合起来，把 Provider 的信任从「相信某个平台」降为「核对几条可离线验证的事实」——这正是本方案把授权主体钉死在部署运营方的意图所在。

## 6. 职责分界总览

| 职责 | 归属 | 说明 |
| --- | --- | --- |
| 建立并保持到上游的连接 | TEE | 凭证注入、Policy 白名单、TLS 记录层、连接生命周期 |
| 回执签发与摘要 | TEE | 请求哈希、下行流式摘要、ProviderSeq 单调序号、签名 |
| 会话的透明字节搬运 | TEE | 只做 TLS 加解密、双向计量、下行摘要，不解析帧 |
| 用户面 API 与会话入口 | Hub | /v1/chat/completions、/v1/messages、/v1/responses、/v1/session |
| 模型到 Provider 的最低价调度 | Hub | 按有效价升序尝试，失败回退次低价 |
| 配额、计价与抽成、账本 | Hub | 整数微单位运算、溢出检查、佣金口径 |
| 回执验签与字节比对 | Hub | 验签后仅当字节与哈希全对上才结算 |
| 会话资源边界 | Hub | 墙钟超时、下行字节上限（截断不结算）、静默看门狗 |
| WebSocket 帧语义 | Hub | 上行掩码客户端帧封装、下行服务端帧解码 |
| 上游的 TCP 密文转发 | Provider Agent | 反向隧道纯字节转发（拨向 Hub 的 AgentGate），不可见任何明文 |

TEE 与 Hub 之间的这条界是 C5 全部工作的主线：TEE 收缩到「连接的建立者与保持者＋字节的搬运者与计量者」，Hub 持有所有需要理解业务含义的逻辑——尤其是计费与帧语义。Provider 的凭证只在 TEE 手里，密钥不出 TEE，而计价与资源边界全部落在 Hub 侧账本上。两端各守一端，谁也不用为另一端的假设背书。
